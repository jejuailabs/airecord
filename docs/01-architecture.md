# 01 — 시스템 아키텍처

> 선행 문서: `core.md`
> 이 문서는 **런타임이 몇 개이고 각각 무엇을 책임지는가**를 정한다. 여기서 정한 경계를 넘는 구현은 하지 않는다.

---

## 1. 핵심 제약: Vercel만으로는 안 된다

가장 먼저 이해해야 할 제약이다. 이걸 모르고 시작하면 Phase 4에서 구조를 갈아엎게 된다.

**실시간 통역은 세션 내내 열려 있는 양방향 스트림을 필요로 한다.** 반면 Vercel의 서버리스/Edge 함수는 요청-응답 수명주기를 전제로 하며, 수십 분짜리 상시 연결 WebSocket 서버 역할에 적합하지 않다.

그래서 모드별로 해법이 다르다.

| | 어떻게 푸는가 | 상시 서버 필요? |
|---|---|---|
| **모드 B (대면)** | 브라우저가 **모델과 직접** WebRTC 연결. Vercel은 임시 토큰(ephemeral token)만 발급. | ❌ 불필요 |
| **모드 A (화상회의)** | 회의 봇이 서버로 오디오를 스트리밍 → 서버가 모델로 릴레이. | ✅ 필요 |

→ **결론: 런타임을 2개로 나눈다.** Vercel(웹앱) + Realtime Worker(상시 컨테이너).

> **왜 모드 B는 직결인가:** 서버를 한 번 경유할 때마다 왕복 지연이 붙는다. 모드 B의 최우선 가치는 지연 최소화(`core.md §3-2`)이므로, 경유 홉을 없애는 것이 옳다. 부수 효과로 서버 비용도 0이 된다. 대가는 사용량 계측의 신뢰 문제이며, 이는 `docs/07 §5`에서 하트비트+서버 정산으로 해결한다.

## 3. 각 런타임의 책임 (경계 침범 금지)

### 3.1 Vercel — Next.js App Router
**한다:** 모든 화면 렌더, 인증 세션, 임시 토큰 발급, 세션 CRUD, 사용량 조회/집계 트리거, 결제 웹훅, 내보내기 파일 생성.
**하지 않는다:** 오디오 바이트를 직접 다루지 않는다. WebSocket 서버를 띄우지 않는다. 30초 이상 걸리는 작업을 동기로 처리하지 않는다.

### 3.2 Realtime Worker — 상시 컨테이너
**한다:** 모드 A의 오디오 릴레이(봇 ↔ 번역 모델), 세그먼트 Firestore 기록, 세션 하드 캡 감시, 봇 이벤트 처리.
**하지 않는다:** UI를 서빙하지 않는다. 유저 인증을 직접 검사하지 않는다(Vercel이 발급한 서명 토큰만 신뢰). 비즈니스 로직(요금제 판정 등)을 갖지 않는다.

- **호스팅 후보:** Cloud Run (Firebase와 같은 GCP 프로젝트 → IAM·네트워크 단순) / Fly.io / Railway.
- **권장:** Cloud Run. 이유는 Firestore·Storage와 같은 프로젝트 안에 있어 서비스 계정 하나로 끝나고, 유휴 시 0으로 스케일 다운되어 고정비가 낮기 때문. **최종 결정 필요** (`docs/02 §6`).

### 3.3 Firebase
**한다:** 인증, 데이터 저장, 파일 저장, 스케줄 집계.
**하지 않는다:** Firestore를 실시간 오디오 버퍼로 쓰지 않는다(쓰기 비용·지연 모두 부적합). 자막 **텍스트** 세그먼트만 기록한다.

## 4. 데이터 흐름

### 4.1 모드 B — 대면 (Phase 1)

```
[1] 유저: 언어쌍 선택 → "통역 시작"
[2] 클라 → Vercel POST /api/session/start
        · 워크스페이스 잔여 분 확인 → 부족하면 402 반환하고 종료
        · sessions/{id} 문서 생성 (status: 'live')
        · 모델 임시 토큰 발급 (수명 짧게, 세션 1회용)
        · { sessionId, ephemeralKey, maxDurationSec } 반환
[3] 클라: WebRTC로 번역 모델에 직결. 마이크 스트림 전송 시작
[4] 모델 → 클라: 부분 전사 / 확정 전사 / 번역 텍스트 (+옵션 번역 오디오)
[5] 클라: 자막 화면 즉시 렌더 (모델 응답을 화면에 그리기까지 서버 경유 없음)
[6] 클라 → Vercel POST /api/session/heartbeat   (10초 주기)
        · 서버가 경과 시간 누적, 캡 초과 시 { terminate: true } 응답
        · 세그먼트를 배치로 함께 전송 (개별 쓰기 금지)
[7] 종료(수동/캡 도달/하트비트 3회 유실)
        → POST /api/session/end → 최종 분 확정 → usage 기록
```

### 4.2 모드 A — 화상회의 (Phase 4)

```
[1] 유저: 회의 URL 붙여넣기 + 언어쌍 선택 → "봇 보내기"
[2] 클라 → Vercel POST /api/meeting/join
        · URL 파싱·검증 → 잔여 분 확인
        · sessions/{id} 생성 (mode: 'meeting', status: 'joining')
        · viewerToken 생성 (자막 뷰어 공개 링크용)
        · Recall.ai 봇 생성 요청 (실시간 오디오 스트림 목적지 = Worker WS 엔드포인트)
[3] 봇: 회의 입장 → 회의 채팅에 자막 링크 자동 게시
        https://<host>/v/{viewerToken}
[4] 봇 → Worker: 오디오 스트림 (WebSocket)
[5] Worker → 번역 모델 → 세그먼트 수신
[6] Worker → Firestore sessions/{id}/segments 에 배치 기록
[7] 뷰어 화면: Firestore 실시간 구독으로 자막 갱신 (인증 불필요, 토큰만으로 read)
[8] 회의 종료 이벤트 → 봇 퇴장 → 세션 종료 → 분 확정
```

> **자막 전달 방식 결정:** MVP는 **웹 링크 방식만** 구현한다. Zoom 네이티브 자막창 연동은 호스트가 자막 API 토큰을 복사해 넣는 절차를 요구하므로 `core.md §3-1`(설정 zero)에 정면으로 어긋난다. Phase 6 이후 재검토.

## 5. 지연 예산 (모드 B 기준)

| 구간 | 목표 | 비고 |
|---|---|---|
| 마이크 캡처 → 모델 도달 | ≤ 150ms | WebRTC 직결이라 서버 홉 없음 |
| 모델 첫 부분 응답 | 벤더 성능에 종속 | 우리가 줄일 수 없는 구간 |
| 응답 → 화면 렌더 | ≤ 50ms | 여기서 리렌더 낭비하면 우리 잘못 |
| **자막 체감 지연 총합** | **가능한 한 낮게, 그리고 누적되지 않게** | 핵심은 절대값보다 **드리프트 없음** |

**설계 지침:**
- 자막은 **부분 전사(partial)를 즉시** 그리고, 확정(final)이 오면 교체한다. 확정을 기다리지 않는다.
- 세그먼트 Firestore 쓰기는 **화면 렌더와 분리**한다. 저장 지연이 자막 지연이 되면 안 된다.
- 번역 **오디오**는 재생 큐가 일정 길이를 넘으면 **오래된 것을 버린다**. 밀린 음성을 끝까지 재생하면 드리프트가 무한히 커진다. (이것이 음성이 2순위인 이유)

## 6. 실패 처리

| 실패 | 동작 |
|---|---|
| 번역 모델 연결 끊김 | 3회 지수 백오프 재연결 → 실패 시 폴백 엔진 시도 → 그래도 실패 시 세션 `degraded` 표시, 자막 화면에 재연결 중 배너 |
| 하트비트 3회 유실 | 서버가 세션을 `orphaned`로 마킹하고 마지막 하트비트 시각까지만 과금 |
| 봇 입장 실패 (모드 A) | 사유별 문구 노출 (대기실 승인 필요 / 잘못된 링크 / 호스트 미시작). 봇 시간 과금 없음 |
| 잔여 분 소진 | 세션 즉시 종료 + 자막 화면에 잔여 없음 안내 + 업그레이드 경로 |
| Firestore 쓰기 실패 | 자막 렌더는 계속 진행. 로컬 버퍼에 쌓고 재시도. **저장 실패가 통역을 멈추면 안 된다** |

## 7. 이 문서에서 확정한 것 / 남은 것

**확정:** 런타임 2분할, 모드 B 직결, 모드 A 워커 릴레이, 자막 웹링크 방식, 세그먼트는 Firestore·오디오는 Storage.
**미확정:** Worker 호스팅 벤더, 번역 모델 최종 선택(1순위/폴백 실측 후 결정), 봇 벤더(Recall.ai 유력하나 대안 존재 — `docs/07 §1.3`).
