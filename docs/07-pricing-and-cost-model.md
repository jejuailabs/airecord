## 1. 원가 단가 — 조사로 확인한 값 (2026-07-26 기준)

### 1.1 번역 엔진

| 모델 | 단가 | 과금 방식 | 출처 |
|---|---|---|---|
| `gpt-realtime-translate` (OpenAI) | **$0.034 / 분** | 오디오 분당 정액 | 2026-05-07 발표 모델. 여러 요금 정리 매체가 동일 수치 보고 |
| `gemini-3.5-live-translate` (Google) | **≈ $0.037 / 분** | 오디오 토큰(초당 25토큰) 기준, 입력 $3.50/1M · 출력 $21/1M | Google 공식 가격 페이지 기준 분당 환산 ≈$0.0368 |

**설계에 영향을 주는 사실**
- 두 단가 차이는 **약 9%뿐**이다. 폴백 전환을 비용 이유로 미루지 않는다(`docs/04 §5`).
- Google 쪽은 **오디오 스트림 단위**로 과금된다. 양방향을 두 스트림으로 구현하면 비용이 2배가 된다. 스트림 수를 명시적으로 세는 습관을 들일 것.
- OpenAI 쪽은 조사 기준 **출력 언어가 입력보다 적다**(입력 70 / 출력 13). 지원 언어를 하드코딩하지 말 것.
- 별도 전사(STT) API를 추가로 붙이지 않는다. 번역 전용 엔드포인트가 전사 텍스트를 함께 주므로, 따로 붙이면 원가가 그냥 늘어난다.

### 1.2 회의 봇 인프라 (모드 A 전용)

| 항목 | 단가 |
|---|---|
| Recall.ai 녹화(봇 체류) | **$0.50 / 시간 = $0.008333 / 분** (초 단위 비례 청구) |
| Recall.ai 내장 전사 | $0.15 / 시간 — **우리는 쓰지 않는다** (번역 엔진이 대체) |
| Recall.ai 녹화 보관 | 7일 무료, 이후 $0.05 / 녹화시간 / 30일 |

**대안 벤더가 존재한다.** MeetStream($0.35/시간 수준 주장), Meeting BaaS(토큰제), Skribby, 자체 호스팅(Attendee 등). 다만 이들 비교 수치는 대체로 **경쟁사 자신의 마케팅 페이지 출처**이므로 그대로 믿지 않는다. 실제 전환 검토는 모드 A 사용량이 월 500시간을 넘은 뒤에 한다. 그 전에는 벤더 교체 엔지니어링 비용이 절감액보다 크다.

### 1.3 신뢰도에 대한 경고
- 위 수치는 **2026-07-26 시점 웹 조사값**이다. 벤더는 예고 없이 가격을 바꾼다(OpenAI 오디오 토큰 단가도 2024년 이후 두 차례 인하된 이력이 있다).
- **분기마다 재확인하고 이 문서를 갱신한다.** 갱신 시 §1 표에 확인 날짜를 다시 적는다.
- 코드에 하드코딩 금지. `COST_TRANSLATE_USD_PER_MIN`, `COST_BOT_USD_PER_MIN` 환경변수로 주입한다(`docs/02 §3`).

## 2. 분당 원가 계산

```
모드 B (대면)   = 번역                    = $0.034
모드 A (화상)   = 번역 + 봇               = $0.034 + $0.008333 = $0.042333

+ 인프라 오버헤드 (Firestore 쓰기 · Cloud Run · Vercel · Storage · 대역폭)
  → 실측 전까지 보수적으로 번역+봇 합계의 10% 를 얹는다

모드 B 실효 원가 ≈ $0.0374 / 분
모드 A 실효 원가 ≈ $0.0466 / 분
```

**원화 환산** (⚠ `USD_KRW_RATE`는 확정값이 아닌 **설정 파라미터**다. 아래는 1,400원 가정.)

| | USD/분 | KRW/분 (1,400 가정) |
|---|---|---|
| 모드 B (대면) | $0.0374 | **약 ₩52** |
| 모드 A (화상) | $0.0466 | **약 ₩65** |
| 혼합 (대면 60% / 화상 40% 가정) | $0.0411 | **약 ₩58** |

> 혼합 비율 60/40은 **가정**이다. 실사용 데이터가 쌓이면 `usage.minutesByMode`로 실제 비율을 뽑아 이 값을 교체한다.

### 계산 코드 (`packages/shared/pricing/cost.ts`)

```ts
export interface CostRates {
  translateUsdPerMin: number;   // env COST_TRANSLATE_USD_PER_MIN
  botUsdPerMin: number;         // env COST_BOT_USD_PER_MIN
  infraOverheadPct: number;     // 0.10
  usdKrw: number;               // env USD_KRW_RATE
}

export function costOfSession(
  mode: SessionMode,
  billedSeconds: number,
  r: CostRates,
) {
  const minutes = billedSeconds / 60;
  const translateUsd = minutes * r.translateUsdPerMin;
  const botUsd = mode === 'meeting' ? minutes * r.botUsdPerMin : 0;
  const base = translateUsd + botUsd;
  const totalUsd = base * (1 + r.infraOverheadPct);
  return {
    translateUsd, botUsd, totalUsd,
    totalKrw: totalUsd * r.usdKrw,
    // 종료 시 sessions/{id}.cost.rateSnapshot 에 r 을 통째로 저장한다.
    // 나중에 단가가 바뀌어도 과거 마진을 재계산할 수 있어야 하기 때문.
  };
}
```

**중요:** 세션 종료 시 그 시점의 단가를 **스냅샷으로 저장**한다(`Session.cost.rateSnapshot`). 단가가 바뀐 뒤 과거 데이터를 현재 단가로 재계산하면 마진 분석이 전부 틀어진다.

## 3. 이 사업의 구조적 특성 (요금제를 설계하기 전에 이해할 것)

일반적인 SaaS는 변동원가가 거의 0이라 매출총이익률 80~90%가 나온다. **이 제품은 다르다.** 유저가 1분 쓸 때마다 실제로 ₩52~65가 빠져나간다.

여기서 나오는 세 가지 원칙:

1. **무제한 요금제를 만들지 않는다.** 헤비 유저 한 명이 플랜 하나의 마진을 통째로 먹는다. 월 300분 플랜(₩49,000)을 한 사람이 3,000분 쓰면 원가만 ₩174,000이다.
2. **포함 분량 + 초과 종량제 하이브리드**로 간다. 정액만으로는 상한이 없고, 종량만으로는 예측 가능성이 없다.
3. **두 개의 마진을 항상 같이 본다.** "포함 분량을 100% 소진했을 때의 최저 마진"과 "실제 사용률 기준 기대 마진". 앞의 것이 무너지지 않게 설계하고, 뒤의 것으로 사업을 판단한다.

## 4. 요금제 설계 — ⚠ 여기부터는 전부 **가설**이다

아래 가격·사용률·전환율은 **검증되지 않았다.** 시장 조사도, 고객 인터뷰도, 경쟁사 실판매가 확인도 아직 없다. 코드에는 설정값으로 넣되, "이 가격이 시장에서 통한다"고 문서나 대화에서 단정하지 않는다. Phase 3 전에 최소 10곳 이상 대상 고객과 가격 대화를 거쳐 교체한다.

### 4.1 플랜 (가설)

| | Free | Team | Business | Enterprise |
|---|---|---|---|---|
| 월 요금 | ₩0 | **₩49,000** | **₩199,000** | 별도 |
| 포함 분 | 30분 | 300분 | 1,500분 | 협의 |
| 분당 실효가 | — | ₩163 | ₩133 | — |
| 초과 종량 | 불가(차단) | ₩180/분 | ₩150/분 | 협의 |
| 멤버 수 | 1 | 무제한 | 무제한 | 무제한 |
| 기록 보관 | 7일 | 90일 | 365일 | 협의 |
| 오디오 저장 | ❌ | 선택 | 선택 | 선택 |
| 모드 A(화상) | ❌ | ✅ | ✅ | ✅ |
| SSO · 계약 · DPA | ❌ | ❌ | ❌ | ✅ |
| BYOK(자체 API 키) | ❌ | ❌ | ❌ | ✅ |

**시트가 아니라 분(minute)으로 과금하는 이유:** 통역이 필요한 사람은 회사 안에서 소수이고, 필요한 순간에만 쓴다. 시트 과금은 "가끔 쓰는 사람"을 배제해 도입 자체를 막는다. 또한 시트 무제한이 `core.md §3-1`(설정 zero)에도 부합한다 — 누가 쓸지 미리 정하지 않아도 된다.

### 4.2 마진 검증 (혼합 원가 ₩58/분 기준)

| 플랜 | 시나리오 | 원가 | 매출총이익 | GM |
|---|---|---|---|---|
| Team ₩49,000 | 포함분 100% 소진 | ₩17,400 | ₩31,600 | **64.5%** |
| | 최악(전량 화상 ₩65/분) | ₩19,500 | ₩29,500 | **60.2%** |
| | 사용률 60% 가정 | ₩10,440 | ₩38,560 | **78.7%** |
| | 초과분 ₩180/분 | ₩58 | ₩122 | **67.8%** |
| Business ₩199,000 | 포함분 100% 소진 | ₩87,000 | ₩112,000 | **56.3%** |
| | 최악(전량 화상) | ₩97,500 | ₩101,500 | **51.0%** |
| | 사용률 60% 가정 | ₩52,200 | ₩146,800 | **73.8%** |
| | 초과분 ₩150/분 | ₩58 | ₩92 | **61.3%** |
| Free | 30분 전량 소진 | ₩1,950 | -₩1,950 | 획득비용으로 간주 |

**해석:** 최악의 경우에도 GM 51% 아래로 내려가지 않는다. 이것이 이 가격표의 방어선이다. **어떤 새 플랜을 만들든 "포함분 100% 소진 + 전량 모드 A" 시나리오에서 GM 50% 이상**을 만족해야 한다.

### 4.3 손익분기 감각 (참고용, 인건비 제외)

인프라 고정비를 월 ₩200,000(Vercel Pro + Cloud Run min-instance + Firebase + 도메인·모니터링) 로 가정하면, Team 플랜 기여이익 ₩31,600 기준 **약 7개 워크스페이스**면 인프라 고정비를 덮는다. 인건비는 포함하지 않았으므로 이 숫자를 사업 손익분기로 착각하지 말 것.

### 4.4 아직 결정하지 않은 것
- 연간 결제 할인율 (통상 2개월분 무료 = 17% 수준이 관행이나 미확정)
- 무료 체험 방식 (Free 플랜으로 갈음 vs Team 14일 체험)
- 부가세 표기 (국내 B2B는 공급가액/부가세 별도 표기 필요 — **확인 필요**)
- 세금계산서 발행 방식 (`docs/02 §6` PG 선택과 연결)

## 5. 미터링 — 어떻게 정확히 세는가

### 5.1 신뢰 모델
모드 B는 브라우저가 모델과 직결되므로(`docs/01 §1`), **클라이언트가 보고하는 시간을 그대로 믿을 수 없다.** 세 겹으로 막는다.

```
[1] 하트비트   클라이언트 → POST /api/session/heartbeat  10초 주기
               서버가 자체 시계로 누적. 클라이언트가 보낸 "경과 시간"은 무시하고
               서버 수신 시각 간격만 센다.
               3회(30초) 유실 → 세션 orphaned, 마지막 하트비트까지만 과금.

[2] 하드 캡    세션 시작 시 서버가 maxDurationSec 을 계산해 내려보낸다.
               = min(SESSION_MAX_DURATION_SEC, 워크스페이스 잔여 분)
               클라이언트도 이 값으로 자체 종료하고, 서버도 하트비트마다 검사한다.
               양쪽 모두 구현한다 — 한쪽만 있으면 뚫린다.

[3] 사후 정산  일 1회 배치가 벤더 사용량 API의 실제 청구 분과
               우리 billedSeconds 합계를 대조한다. §6 참조.
```

### 5.2 과금 규칙
- **초 단위로 세고, 세션당 올림하여 분 단위로 청구**한다. 30초 세션도 1분으로 과금(우리 실원가도 그렇게 나가므로).
- 봇 입장 실패, 대기실에서만 머무른 시간은 **과금하지 않는다.**
- `degraded` 상태(폴백 중 자막이 끊긴 구간)는 과금에서 제외한다. 세션 문서에 `degradedSeconds`를 따로 누적한다.
- 잔여 분이 0이 되면 **진행 중인 세션도 종료**한다. 단 종료 30초 전에 자막 화면에 경고를 띄운다. 예고 없이 끊지 않는다.

### 5.3 예산 보호 (유저용)
- 워크스페이스 관리자는 `hardCapMinutes`(월 예산 상한)를 설정할 수 있다. 도달하면 초과 종량 과금이 있어도 차단한다.
- 포함 분의 80% · 100% 도달 시 관리자에게 메일 알림.
- `overageEnabled: false`가 기본값이다. **유저가 명시적으로 켜야** 초과 과금이 발생한다. 예상치 못한 청구서는 해지 사유 1순위다.

## 6. 실제 청구액과 대조 (필수)

우리 계산이 벤더 실청구와 어긋나는 건 흔한 일이다. **Phase 3 이전에 반드시 한 번 검증한다.**

```
일 1회 Cloud Function:
  1. usage/{ws}/daily 의 costUsd 합계 산출
  2. 벤더(OpenAI/Google/Recall) 사용량 API에서 같은 날짜 실제 사용량 조회
  3. 괴리율 = |우리계산 - 실제| / 실제
  4. 괴리율 5% 초과 → 관리자 알림 + 대시보드에 경고 배지
```

**괴리가 나는 흔한 원인:**
- 세션 연결 수립·정리 시간이 청구에 포함됨 (우리는 안 세고 있을 수 있음)
- 침묵 구간 처리 방식 차이
- 봇이 대기실에 머문 시간이 청구에 포함됨
- 재연결 시 세션이 새로 열려 중복 과금
- 환율 적용 시점 차이

괴리 원인이 밝혀지면 `infraOverheadPct`가 아니라 **계산식 자체를 고친다.** 오버헤드 퍼센트로 얼버무리지 않는다.

## 7. 요약: 이 문서에서 무엇이 사실이고 무엇이 아닌가

| 구분 | 내용 |
|---|---|
| **조사로 확인** | 번역 엔진 분당 단가, 봇 시간당 단가, 과금 방식 (§1) — 단, 2026-07-26 기준이며 변동함 |
| **계산으로 도출** | 분당 실효 원가, 플랜별 마진 (§2, §4.2) — 위 단가와 가정이 맞다는 전제에서만 유효 |
| **가정** | 인프라 오버헤드 10%, 환율 1,400원, 모드 혼합 60/40, 사용률 60% |
| **검증 안 된 가설** | 플랜 가격, 포함 분량, 초과 단가, 시장 수용성, 경쟁 상황 (§4) |
| **모르는 것** | 국내에 이 형태의 제품 수요가 실제로 있는지, 얼마를 낼 의향이 있는지. **조사한 바 없다.** |
